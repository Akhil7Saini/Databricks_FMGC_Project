Atlon × Sports Bar: the complete project guide

A unified data platform on Databricks Free Edition. This single file explains the business problem, the architecture, every layer of the pipeline with its code (what, why and how), the orchestration, the denormalised view, Genie and the dashboard, plus verification steps and interview questions.

How to read it. Sections 1 to 4 give the big picture. Sections 5 to 9 walk through the pipeline in the order it runs. Sections 10 to 14 cover the job, the serving layer and checks. Inside the detailed code sections, step numbers such as 1.1 or 3.3 refer to that section only. Click the questions in the interview sections to reveal answers.

1. The project at a glance

The business story

Atlon manufactures sports equipment and runs a mature data platform: an OLTP system feeding Bronze, Silver and Gold layers on Databricks, with BI dashboards and Genie on top. Atlon acquired Sports Bar, a startup selling energy bars and athletic nutrition. Sports Bar has only an OLTP database and Excel dashboards. Leadership kept Sports Bar’s teams and processes and does not want a multi-year migration right now, but the CEO wants one dashboard showing revenue and top products across both companies.

The task: build a reliable data layer for Sports Bar, merge it into Atlon’s Gold layer, and serve combined analytics. The Atlon pipeline is left untouched.

4. Environment setup

4.1 Catalog and schemas

What Create the catalog fmcg and its three medallion schemas.
Why Unity Catalog organises data as catalog → schema → table. Separate schemas per layer keep raw, clean and curated tables apart and make permissions and clean-up simple.
How
  • CREATE … IF NOT EXISTS makes the cell safe to rerun.
  • USE catalog fmcg sets the default catalog for the notebook.
  • SHOW DATABASES FROM fmcg lists the schemas to confirm. default and information_schema appear automatically.

4.2 Loading Atlon’s Gold tables from CSV

In real life Atlon’s pipeline already exists. In this learning project the four Atlon files from full_load were uploaded into fmcg.gold through the Data Ingestion screen: dim_customers, dim_products, dim_gross_price and fact_orders (about 93,000 rows).

  • The destination schema must be gold, not default.
  • customer_code was changed from integer to string, and so were the other codes. A code is a label, not a number to calculate with, and Sports Bar’s codes are also strings.
  • Afterwards a SELECT COUNT(*) on the fact table confirms the row count against the CSV.

4.3 The date dimension

What Generate a table with one row per month from January 2024 to December 2025, with ready-made calendar attributes.
Why Dashboards group by year, quarter and month. A calendar dimension provides those attributes once, so every report uses the same definitions. Generating it with code avoids importing a CSV.
How
  • sequence(start, end, interval 1 month) creates an array of month-start dates; explode turns the array into one row per date.
  • date_format(date, "yyyyMM") turns 2025-07-01 into 202507, which becomes the integer date_key.
  • F.year, F.quarter and date_format(..., "MMMM") extract year, quarter number and month name; concat builds labels such as Q3 and 2025-Q3.
  • mode("overwrite") replaces the table each time the notebook runs.
Watch out. The table stops at 2025-12-01. Orders dated later get null date attributes in the view until you extend end_date and rerun.

4.4 Raw landing and processed catalogs

What Create separate catalogs for raw landing files and for archived (processed) files, with one volume per source.
Why S3 was not available, and Free Edition does not allow external storage. A volume is Unity Catalog storage for files (as opposed to tables), so it can play the part of the S3 bucket. Keeping raw and processed files in their own catalogs mirrors the folder structure of the course data and keeps raw data separate from curated tables.
How
  • A volume’s files live under /Volumes/<catalog>/<schema>/<volume>/, for example /Volumes/raw_data_fmgc/full_load/customers/customers.csv.
  • Files are uploaded through the Catalog UI (Upload to this volume). Each CSV must sit directly inside its volume, because the notebooks read …/<volume>/*.csv.
  • The processed volumes stay empty until the notebooks move files into them after loading.

5. PySpark and regex foundations

These building blocks appear in almost every notebook below. Read this section once and the code sections become easy to follow.

Silver is the clean layer. Bronze keeps the data exactly as it arrived (with all its mistakes). Silver fixes those mistakes so Gold can safely reshape the data into the parent company’s model. Before the steps, here are the building blocks that appear again and again.

DataFrames never change in place

A Spark DataFrame is like a table you can look at but not edit. Every operation (withColumn, filter, join, drop…) returns a new DataFrame and leaves the old one untouched. That is why you always see a reassignment:

If you wrote only df_silver.withColumn(...) without the df_silver = part, the result would be thrown away and nothing would change.

F and F.col

from pyspark.sql import functions as F

pyspark.sql.functions is PySpark’s library of column functions (trim, initcap, sha2, coalesce…). as F is just a short nickname, so you write F.trim(...) instead of functions.trim(...). These functions don’t run on their own: they describe an operation, and Spark applies it to every row when the DataFrame is actually used.

F.col("customer_name")

A reference to the column called customer_name. You need it whenever you compare or calculate with a column, for example F.col("count") > 1 or F.col("gross_price").cast("double") < 0. Many functions also accept the plain name as a string (F.initcap("customer_name"), F.coalesce("city", "fixed_city")), which is a shortcut for the same thing.

F.lit: put a constant into a column

F.lit(value)

lit means literal. Spark works with columns, not loose Python values, so a fixed value has to be wrapped to become a column in which every row holds that same value. Without lit, df.withColumn("market", "India") fails because "India" is a Python string and not a column. With F.lit("India") it works.

RowBefore .withColumn("market", F.lit("India"))After
Atlon-style row 1(no market column)India
row 2(no market column)India
row 3(no market column)India

Where it is used in Silver: F.lit("India"), F.lit("Sports Bar"), F.lit("Acquisition") (fixed business values), F.lit("Unknown") (a fallback value inside coalesce) and F.lit(999999) (the fallback product id).

withColumn: add or replace a column

df.withColumn("name", expression)

Takes a column name and an expression. If the name does not exist yet, a new column is added. If it already exists, the column is replaced. Chaining several calls in brackets applies them one after another.

CallEffect
.withColumn("market", F.lit("India"))adds a new column market
.withColumn("customer_name", F.trim("customer_name"))overwrites the existing column

F.when(...).otherwise(...): if / else for columns

F.when(condition, value).when(...).otherwise(default)

The column version of SQL’s CASE WHEN. Spark checks the conditions from top to bottom for each row and uses the first one that is true. otherwise is the fallback. If you leave out otherwise and nothing matches, the result is null.

F.coalesce: take the first value that is not null

F.coalesce(a, b, c, …)

Looks at its arguments from left to right and returns the first one that is not null. If all are null, the result is null. Think of it as “use a, but if a is missing use b, and if that is missing too use c”. (It is unrelated to DataFrame.coalesce(n), which reduces the number of partitions.)

Regular expression cheat sheet

A regular expression (regex) is a pattern language for matching text. Four notebook steps use one: regexp_replace, regexp_extract, rlike, and the (?i) flag. These are the pieces you will meet:

SymbolMeaningExample

*previous item, zero or more times.* means “anything, any length”
+previous item, one or more times[0-9]+ means “one or more digits”

6. Sports Bar dimension pipelines (customers, products, pricing)

Three notebooks (1_customers_data_processing, 2_products_data_processing, 3_pricing_data_processing) follow the same pattern: Bronze (raw copy) → Silver (cleaning) → Gold (child table) → merge into the parent dimension. Dimensions are small and are fully reloaded, so the notebooks overwrite their child tables on every run.

6.1 Bronze (the same pattern in all three notebooks)

What Read the CSV from its volume, add three audit columns and save it unchanged as fmcg.bronze.customers.
Why Bronze is the permanent raw copy, so later layers can be rebuilt without going back to the files. The audit columns record where and when every row came from.
How
  • spark.read.format("csv") with header=True uses the first line as column names; inferSchema=True makes Spark guess types (so customer_id becomes an integer).
  • .load(".../customers/*.csv") reads every CSV in the volume; * is a wildcard.
  • read_timestamp is the load time; _metadata.file_name and file_size are Spark’s hidden file metadata. Together they give lineage and help debugging.
  • mode("overwrite") replaces the table, which suits a small dimension reloaded in full. delta.enableChangeDataFeed records row-level changes.
  • printSchema() and display(...) are only checks and change nothing.

Interview questions and answers

Click a question to see an answer you could give.

Walk me through this pipeline end to end.

Sports Bar’s OLTP data is exported as daily CSV files into a landing volume. A notebook reads all files into Bronze with append, adds read time, file name and size, then moves the files to a processed volume. Silver cleans the data (null quantities, invalid customer ids, mixed date formats, duplicates), joins to the Silver products table to get product_code, and writes with an upsert. Gold renames the columns to the parent’s schema, also with an upsert. Finally the daily data is aggregated to monthly grain and merged into the parent’s fact_orders, so both companies are in one table.

Why do you move files to a processed folder?

So that the landing folder holds only unprocessed files. Bronze is loaded with append, so loading the same file twice would duplicate rows. Moving files after a successful load makes reruns safe, makes daily processing simple (everything in landing is new), and keeps the raw files for audit or reprocessing.

Why append in Bronze but overwrite for the dimension tables?

Dimensions are small and are fully reloaded each time, so overwrite gives a clean copy. A fact table grows with every file, and each file is new data, so Bronze appends. Overwriting would delete the history.

What is the _metadata column?

A hidden column Spark exposes for file-based reads. It has file_name, file_size, file_path and file_modification_time. We select file_name and file_size to record lineage, so any bad row can be traced to its source file.

What does inferSchema do and what is the downside?

It makes Spark scan the data to guess column types. It is convenient but costs an extra pass and the guess can change if the data changes (for example a column that becomes text because of one bad value). In production you would define the schema explicitly. In Bronze it is acceptable because types are fixed in Silver.

How do you handle the many date formats?

First strip the weekday prefix with regexp_replace. Then try each known format with try_to_date, which returns null on a mismatch instead of failing, and use coalesce to take the first successful parse. Anything that matches no format ends up null, so you should monitor for null dates.

Why is deduplication done after the date is parsed?

Duplicates may be written with different date text, so they look different as strings. After parsing, they are identical and dropDuplicates can recognise them.

Why not use order_id alone as the key?

One order can have several product lines, so order_id repeats. The key is a combination: order_placement_date, order_id, product_code and customer_id.

What is an upsert and why use MERGE instead of append or overwrite?

Upsert means update existing rows and insert new ones in one atomic operation, based on key columns. Append would create duplicates on reruns, and overwrite would lose history. MERGE makes the load idempotent and works for both the full load and later incremental loads.

Explain whenMatchedUpdateAll and whenNotMatchedInsertAll.

When a source row matches a target row on the condition, whenMatchedUpdateAll updates all target columns with the source values. When a source row matches nothing, whenNotMatchedInsertAll inserts it. execute() runs the merge. The source columns must have the same names as the target’s.

What error can a Delta MERGE raise and when?

“Multiple source rows matched the same target row.” It happens when the new data contains two rows with the same key. You prevent it by deduplicating the source on the merge key before merging.

Why does the Silver join select df_orders["*"] and only product_code?

The products table has columns with the same names as the orders table (read_timestamp, file_name, file_size). Joining everything would create duplicate column names and ambiguity errors. Selecting all order columns plus just product_code avoids that.

Why an inner join with products? What are the risks?

We only want orders for known products, and product_code is needed for the parent key. The risk is silent data loss: orders for unknown products are dropped. You should compare counts before and after, and consider a left join with a quarantine table for unmatched rows. Also, if product_id is not unique in the products table, the join multiplies rows.

The parent table is monthly and the child is daily. How did you reconcile them?

I truncated each date to the first of the month with F.trunc(date, "MM"), grouped by month, product code and customer code, summed sold_quantity, and renamed the column back to date. Then I merged the monthly rows into the parent table.

Why does the final merge replace sold_quantity instead of adding to it?

Because the monthly total is always recomputed from the whole child Gold table. Replacing with the recomputed total is correct and idempotent, while adding would double-count on every rerun.

What is lazy evaluation? Give an example from this notebook.

Transformations such as filter, withColumn, join and groupBy only build an execution plan. Spark runs it when an action such as show, count or write is called. In this notebook, all six Silver rules do nothing until show() in the date check or the Silver write.

What is Change Data Feed and why enable it?

A Delta feature that records row-level changes (inserts, updates, deletes) with the table. It lets downstream consumers read only what changed and supports auditing. It is set with delta.enableChangeDataFeed = true when the table is created.

What would you improve in this notebook for production?

Use an explicit schema instead of inferSchema. Count and alert on null dates, null quantities, unknown customers and unmatched products instead of silently dropping or nulling them. Quarantine rejected rows. Add explicit error handling so files are moved only after a successful write. Read only new Bronze rows for Silver on incremental runs instead of the whole table. Replace the shared 999999 placeholder with a documented unknown-member row in the dimension.

How will the December incremental load differ?

The same steps are used, but only the new files are in landing. Bronze appends them, they are moved to processed, Silver and Gold merge the new rows, and the monthly aggregate is recomputed and merged into the parent. Because of the merges, nothing already loaded is duplicated.

3.5 Write Silver: create the first time, MERGE afterwards

What If the Silver table does not exist, create it. If it already exists, upsert the new rows into it.
Why Orders keep arriving (the December files are next), and reruns happen. Overwriting would lose history, and appending would create duplicates. A merge adds new rows and refreshes existing ones, so the table is always correct no matter how many times the notebook runs.
How
  • spark.catalog.tableExists("...") returns true or false. if not (...) takes the first branch only on the very first run.
  • First run: a normal write. mode("overwrite") is safe because the table does not exist; mergeSchema lets the schema be created from the DataFrame; change data feed is switched on.
  • Later runs: DeltaTable.forName(spark, "fmcg.silver.orders") opens the existing table as a Delta table object.
  • .alias("silver") names the existing (target) table so the condition can say silver.xxx.
  • .merge(df_joined.alias("bronze"), condition) supplies the new data (the source), labelled bronze in the condition, and the matching rule.
  • The condition matches rows on four columns: order_placement_date, order_id, product_code, customer_id. Together they identify one order line (the order id alone repeats for each product in an order).
  • .whenMatchedUpdateAll(): for rows that match, overwrite all columns with the new values.
  • .whenNotMatchedInsertAll(): for new rows that match nothing, insert them.
  • .execute() runs the merge. Without it nothing happens.

Interview questions and answers

Click a question to see an answer you could give.

How is this load incremental?

Only new files are processed. New files sit in a landing folder, loaded files are moved to an archive, and the new rows pass through staging tables so that Bronze-to-Silver and Silver-to-Gold work only on the new batch. The history is updated with merges, and the parent’s monthly totals are recomputed only for the months present in the batch.

You upload files to a Volume by hand, not S3. Is it still incremental?

Yes. Incrementality comes from the notebook logic, which reads whatever is in the landing folder and then moves it out. The storage location (S3 or a Volume) and who puts the files there only change how files arrive. In production the delivery and the run would be automated with an export job and a scheduled or file-arrival-triggered job.

What is a staging table and why do you need one?

A table that holds only the current batch. Bronze and Silver contain the full history, so they cannot tell the next layer which rows are new. The staging table, overwritten each run, gives the next layer exactly the new rows, so it never reprocesses history.

Why overwrite the staging tables but append to Bronze?

Bronze is the permanent raw history, so new rows are added. Staging is temporary and must contain only the latest batch, so it is replaced on each run.

Why must the move-files cell come after the staging write?

The DataFrame df is lazy and is not stored. Each action, including each write, re-reads the files from landing. If the files were moved before the staging write, it would find no files. So the order is: read, write Bronze, write staging, then move.

What happens if the notebook fails after the Bronze append but before the files are moved?

The files stay in landing, so the next run reads them again and appends them to Bronze a second time. Bronze then has duplicates. Silver and Gold stay correct because merges match on the key columns and update instead of duplicating, and the parent totals are recomputed from child Gold. A safer design moves files only after all writes succeed, or deduplicates Bronze, or uses a tool that tracks processed files.

Why is Silver read from the staging table and not from Bronze?

Bronze holds the entire history, which is already cleaned in Silver. Cleaning it again would waste time and grow with the data. Reading only the staging rows keeps the work proportional to the size of the new batch.

Why does the parent step recompute the whole month instead of adding the new quantity?

The merge replaces matched rows. If you merged only the new day’s quantity, the month’s total would be overwritten with a partial value. Recomputing from child Gold, which has every day of the month, produces the correct complete total, and it is idempotent: running it twice gives the same result.

What are incremental_months and what is a temp view?

incremental_months is a one-column DataFrame holding the first day of each month that appears in the new batch. createOrReplaceTempView registers it under a name so the next cell can join to it in SQL. A temp view stores no data and lasts only for the session.

What would happen if a file with last month’s data arrives late?

The month start of those rows is in incremental_months, so that month’s daily rows are fetched from child Gold, its totals are recomputed, and the parent’s rows for that month are updated. This is why the design copes with late-arriving data.

What if the same file is uploaded twice?

Bronze would hold its rows twice because it appends. In Silver and child Gold, the merge keys match the existing rows, so they are updated, not duplicated. The monthly totals are recomputed from child Gold, so the parent stays correct. You would still clean up the Bronze duplicates or prevent the repeat delivery.

Why is there no staging table in Gold?

Gold is the last step for the child company. The new rows just have to be merged into the child Gold table, and the parent step reads the dates from the Silver staging table. Nothing further downstream needs a separate Gold batch.

Why are both staging tables dropped at the end?

They only carry one batch. Dropping them prevents a stale batch from being picked up if a later run fails early. The next run recreates them with overwrite.

Explain whenMatchedUpdateAll and whenNotMatchedInsertAll.

When a new row matches an existing row on the merge condition, whenMatchedUpdateAll updates all its columns with the new values. When it matches nothing, whenNotMatchedInsertAll inserts it. execute() runs the operation. The source columns must have the same names as the target’s.

Which merge keys are used and why?

Silver: order date, order id, product code and customer id. Child Gold: date, order id, product code and customer code. Parent: month date, product code and customer code. An order id repeats for each product line, so a combination of columns is needed to identify a row.

When can a Delta merge fail, and how would you avoid it?

With a “multiple source rows matched” error if two new rows have the same key but different values, for example the same order line twice in one batch with different quantities. Deduplicate the source on the merge key (keeping the latest) before merging.

How would you automate this in production?

Have the source system deliver files to the landing location, and run the notebook as a Databricks Workflows job on a nightly schedule or with a file-arrival trigger. Alternatively use Auto Loader or COPY INTO, which keep track of ingested files themselves.

What is the difference between a full load and an incremental load?

A full load processes all the history in one batch (here July to November). An incremental load processes only new data each run and merges it into what already exists. The transformations are the same, but the incremental notebook adds staging tables and restricts the parent recomputation to affected months.

How would you check that the incremental run was correct?

Compare Bronze’s row count before and after with the rows in the new files. Check that each file name appears once in Bronze. Confirm that the December total in child Gold (daily) equals the Sports Bar part of the parent’s December monthly row. Check that the landing folder is empty and the files are in the processed volume.

What would you improve before using this in production?

Automate delivery and execution, move files only after all writes succeed, track processed files with Auto Loader or COPY INTO, quarantine rejected rows instead of silently dropping them, add monitoring for nulls and unmatched keys, and filter child Gold by a date range to let Delta skip files.

14. Interview questions about the whole project

Click a question to see an answer. Each detailed section above also has its own questions.

Explain the project in two minutes.

Atlon, a sports equipment manufacturer, acquired Sports Bar, a startup whose data lived in an OLTP database and Excel reports. Leadership wanted combined analytics before any system migration. I built a medallion pipeline on Databricks: Sports Bar’s files land in volumes, go to Bronze as raw Delta tables, are cleaned in Silver, reshaped in Gold and merged into Atlon’s Gold tables. The history was backfilled once, and new daily files are processed incrementally with staging tables and MERGE. A flat view feeds a Genie space and a dashboard showing both companies together.

Why a medallion architecture?

It separates raw, clean and curated data. Raw data is kept unchanged so you can rebuild downstream layers, each layer has one purpose, and problems are easy to locate.

The tutorial used S3. How did you adapt it when S3 was not available?

Databricks Free Edition does not allow external locations, so I used Unity Catalog volumes as the landing and archive areas. The pipeline logic is unchanged, because it only needs a folder of files. Only who delivers the files and who starts the run are manual.

How did you make the pipeline safe to rerun?

Dimensions are overwritten, Silver, Gold and the parent are loaded with MERGE on key columns, the monthly totals are recomputed from complete data and merged, COPY INTO tracks loaded files, and Bronze appends are protected by moving loaded files out of landing.

How did you deal with different grains in the parent and child data?

Sports Bar’s Gold table stays daily. Before merging into the parent’s monthly fact table I truncate dates to the first of the month, group by month, product and customer, sum the quantities, and rename the date column. The merge replaces matched months with the recomputed total.

Why did you generate product_code with a hash?

Sports Bar’s product ids contained invalid values, and the parent identifies products by product_code. A SHA-256 hash of the cleaned product name is deterministic and unique per name, so it can be recreated on every run. The caveat is that two products with the same name would collide.

What data quality issues did you find and how were they handled?

Duplicates (dropDuplicates), spaces (trim), capitalisation (initcap), typos (replace and regexp_replace), missing cities (business-confirmed mapping), invalid ids (placeholders), mixed date formats (try_to_date with coalesce), negative and non-numeric prices (rules agreed with the business) and missing quantities (rows removed).

Why are staging tables used in the incremental load?

Bronze and Silver hold the full history, so they cannot tell the next layer which rows are new. The staging tables hold only the current batch, so each layer works on the new data only.

Why recompute the whole month for the parent instead of adding the new quantity?

The parent merge replaces matched rows. Adding only the new day’s quantity would overwrite the month’s total with a partial number. Recomputing from child Gold, which has every day, gives the correct total and is idempotent.

How is the job orchestrated?

A Databricks job with four notebook tasks in a chain: customers, products, pricing, then the incremental fact notebook. Each task runs only if the previous one succeeded. It is meant to run nightly with a Quartz cron schedule and failure emails. It has no parameters because the notebooks have no widgets.

What is the denormalised view and why did you create it?

A view that left-joins the fact table to all dimensions and adds a revenue column. It gives analysts, Genie and the dashboard one table with everything in it, so nobody writes joins and the revenue formula is defined once. Left joins keep every order even when a dimension row is missing.

What can go wrong with that view?

Duplicate dimension keys inflate revenue, missing prices give null revenue, unknown customers produce null attributes, and dates beyond the date dimension have null calendar fields. I check by comparing the view’s row count with the fact table and counting nulls.

How did you validate the numbers?

Row counts against the files (93,055 plus 4,485 Atlon rows, 97,540 in total), the COPY INTO inserted count, the child daily total against the parent monthly total, and a recomputation of revenue from the CSV files to explain the dashboard totals.

What is Genie and how would you use it responsibly?

Genie turns natural-language questions into SQL over a chosen dataset. It is quick for exploration, but I read the generated SQL and compare key results with known totals before trusting them.

What would you change to make this production ready?

Automate file delivery and run the job on a schedule or file-arrival trigger, track ingested files with Auto Loader or COPY INTO, use explicit schemas, quarantine rejected rows, add monitoring for nulls and unmatched keys, fix the price merge key to include the year, and add an Unknown member to the dimensions.

What did you learn from this project?

Data engineering is mostly making messy inputs reliable: understanding the data first, agreeing business rules, designing for reruns and late data, and proving the numbers reconcile.
